## 3. Правки, меняющие смысл

Порядок — по убыванию цены ошибки. Форма — четыре поля. Слово «Стало» везде означает готовый текст, вставляемый как есть.

### П1 🔴 Прочистка (`docker … prune`) предписана без эскалации в трёх местах при запрете в четвёртом — и это ровно тот случай, ради которого заведён запрет

**Было:**
- `playbooks/prod_escalation.md:13` — «Что считается production-affecting (эскалировать): 1. `docker prune` (любой), volume operations, image deletion.»; `:29` — «Что НЕ требует эскалации: … Build-cache prune без image deletion (если согласовано как routine)»; `:79` — «Реальный кейс: DO-01 при ENOSPC сам выполнил `docker builder prune -af && docker image prune -af`, освободил место и продолжил deploy. … затронуло rollback (старые images снесены). … Self-judgment агента = риск.»
- `playbooks/deploy_workflow.md:10` — «Должно быть **< 70% used**. Если выше → `docker system prune -af --filter "until=72h"`, проверить ещё раз. Только потом — миграции и build.»; `:20` — «Reclaimable < 2 GB. Иначе prune.»; `:92` — «2. `docker system prune -af --filter "until=72h"` (или `--volumes` если согласовано Big 7).»
- `templates/agent_briefing.md:42` — «Pre-flight: `df -h /` must be <70%; if higher → `docker system prune -af --filter "until=72h"` first.»; `:47` — «On ENOSPC: STOP, prune, retry migration».

`docker system prune -a` удаляет **все неиспользуемые образы**, то есть именно «image deletion» из пункта 1 списка эскалации, и именно то, что в «Реальном кейсе» снесло откат. Брифинг вставляется в начало **каждого** промпта исполнителя (`agent_briefing.md:3`), и в том же брифинге строкой 24 стоит «prune → STOP, ESCALATING TO HR-D». Исполнитель получает в одном документе «prune → стоп» и «prune first».

**Стало** (три входа одним ходом):

`playbooks/deploy_workflow.md`, строки 10 и 20 → заменить на:

> - Должно быть **< 70% used**. Если выше — сначала то, что разрешено без эскалации (`playbooks/prod_escalation.md`, «Что НЕ требует эскалации»): `docker builder prune -f --filter "until=72h"` — это кэш сборки, образы не трогаются. Проверить `df -h /` ещё раз. Если всё ещё выше 70 % — **STOP, эскалация в ядро** (`prod_escalation.md`, пункт 1: прочистка образов и томов — production-affecting, потому что сносит образы для отката). Только после этого — миграции и build.
> - Reclaimable < 2 GB. Иначе — тот же порядок: кэш сборки сам, образы — через эскалацию.

`playbooks/deploy_workflow.md`, строка 92 → заменить на:

> 2. `docker builder prune -f --filter "until=72h"` (кэш сборки — без эскалации). Не хватило — **STOP, эскалация в ядро**: `docker system prune -a`/`image prune`/`--volumes` — пункт 1 списка production-affecting, решает ядро, а не исполнитель (случай DO-01 в `prod_escalation.md`, «Почему правило существует»).

`templates/agent_briefing.md`, строки 42 и 47 → заменить на:

**Стало** (раздел строк 15–29 целиком):
> ## Приостановка или прекращение зеркалирования — как выглядит
>
> Зеркалирование может быть **приостановлено или прекращено владельцем** — тогда push в зеркало пропускается, и правило не нарушено. Решение обязано быть **записано в памяти проекта** с датой и признаком: приостановка — с условием снятия, прекращение — с новым статусом бывшего зеркала (обычно «только чтение/архив»). Действующие решения в тексте этого стандарта не живут (проектное — в проекте, `knowledge/README.md`); здесь — только форма:
>
> ```bash
> git push <адрес-записи> <branch>
> # git push <зеркало> <branch>   # ⏳ приостановлено владельцем <дата>, условие снятия — в памяти проекта;
> #                               #    имя зеркала — из git remote -v, не из памяти
> ```
>
> Приостановленную строку держать закомментированной с меткой `⏳`, датой и адресом записи: удаление потеряет то, что придётся возвращать. **Прекращённое** зеркалирование (владелец решил насовсем) — строку удалить вместе с меткой, оставив в памяти проекта запись «зеркало X прекращено <дата>, статус — только чтение/архив»: закомментированная строка без условия снятия — постоянная оговорка (`git-branch-discipline.md`, «Срок оговорки»).
>
> Насколько разошлось зеркало — измерять, а не предполагать, и измерять после `fetch`: `git fetch <зеркало> && git rev-list --count <зеркало>/master..master`. Ноль означает, что зеркало догнало. Без `fetch` число говорит о свежести локального ref, а не о состоянии зеркала — 19.08.2026 эти две неисправности дали одинаковый симптом и были разведены только свежим чтением. Конкретную величину здесь не фиксируем: она меняется ежедневно, а правило — нет.

> ## Шкала (сверху вниз; первый подходящий пункт решает)
>
> 1. **Обратимо, путь один → делаю и коротко отчитываюсь.** Мелкие правки в рамках задачи, чтение/диагностика, обратимые шаги, очевидный единственный путь. Мелочь — это: имя переменной, расположение файла по конвенции, формат лога, очевидная идиома.
>    - **1а. Проверяемый факт → проверяю сам, не спрашиваю.** В автономном режиме ЛЮБОЙ факт, устанавливаемый недеструктивной пробой (порт слушает? сервис отвечает? файл есть? какая версия?), — устанавливать самому: curl/ss/dig/nc/read-only SQL, а не вопросом «а ты включил?». Перед вопросом «сделал ли ты X?» — сначала проверить X. Owner, 2026-07-19, дословно: «Ты сам проверить же можешь, есть форвардинг или нет. Без дестроя в автономном режиме проверяй сам всегда.» Развилки решений в автономном режиме — через ядро, не через владельца (запись — в памяти проекта; в MDMy — `feedback_autonomous_no_owner_questions`).
> 2. **Двоякость формулировки → переспросить.** Фраза с ≥2 трактовками → короткий вопрос «верно понял: X?» до реализации (`playbooks/workflow_loop.md`, п. 1). Не подменять уточнение догадкой ради скорости: цена неверного предположения выше цены вопроса.
> 3. **Развилка (2+ одинаково правильных пути) → спросить, не выбирать за владельца.** Какой подход, какой scope, какое устройство, какой дефолт — решение владельца. Развилка отличается от мелочи тем, что разные пути дают разный результат, который владелец оценил бы по-разному. Агент на развилке паркуется, а не угадывает ([[agent-question-rendezvous]]).
> 4. **Необратимо / деструктив / прод → явное подтверждение, даже если путь один (HARD).** Drop/wipe/flash/delete, прод-disruption, finish/релиз, физические последствия (reboot устройства, остановка службы), установка системного софта ([[no-silent-installs]]). Порядок — `playbooks/prod_escalation.md`, `[[validate-recovery-before-destructive]]`.
> 5. **Решение владельца выглядит слабым → возразить с фактами, потом исполнять (HARD).** «Слабое» — широко: фактически ошибочное, субоптимальное, рискованное, противоречащее HARD-правилам/архитектуре/известным находкам, основанное на устаревшем предположении. Форма: коротко и уважительно — (1) в чём проблема и почему (факт/правило/прецедент), (2) 1–2 альтернативы с трейдофами, (3) рекомендация. Решение за владельцем; подтвердил — исполняем (кроме необратимого деструктива на проде без обоснования — ступень 4 сильнее). Применять и к собственным прошлым советам: нашёл, что советовал неоптимально, — сказать. Молча исполнять заведомо проигрышное = нарушение: владелец полагается на то, что ассистент видит код и подсветит.
> 6. **Вопрос или сомнение владельца → probe, а не оправдание.** Владелец — эксперт; «а почему так?», «точно работает?» — сигнал проверить на фактах (код/данные/прод) и только потом отвечать. «Всё хорошо» по памяти — антипаттерн: владелец часто видит проблему раньше. Вопрос «зачем X?» = возможно, X избыточен — пересмотреть, а не защищать.

> # Standard: повторяющийся шаг — к обязательному действию, а не к памяти человека
>
> **Статус:** обязательный · **Применимость:** любой проект; любой повторяющийся шаг сопровождения — перенос памяти в репозиторий, синхронизация зеркала, резервная копия, обновление указателя, — который держится на «не забывать делать».
> **Происхождение:** MDMy, 19.06–22.08.2026 (раздел «Случай»); формулировка — исполнителя MDMy, 24.08.2026.
>
> ## Правило
> **Ручной повторяющийся шаг перестаёт делаться ровно тогда, когда работы много, — то есть когда он нужнее всего.** Поэтому шаг, от которого зависит сохранность данных или работоспособность, либо встраивается в действие, которое исполнитель и так обязан совершать — и это действие отказывает, пока шаг не выполнен, — либо честно объявляется отсутствующим: «делаем руками, когда вспомним» защитой не считается.
>
> 1. **Носитель — обязательное действие**, мимо которого нельзя пройти к цели исполнителя: выкат, merge, гейт старта сессии. Не расписание и не напоминание: у расписания есть свой ручной шаг («посмотреть, что упало»), и умирает он под той же нагрузкой.
> 2. **Отказ, а не предупреждение.** Механизм обязан уметь остановить носителя (ненулевой код возврата, красный гейт): предупреждение пролистывают ровно тогда же, когда забывают ручной шаг.
> 3. **Признак несрабатывания назван при введении** (Б1): по какому наблюдаемому состоянию видно, что механизм перестал защищать. Пример из случая: живой файл памяти недостижим из удалённых веток → выкат отказывает кодом 4.
> 4. **Граница.** Не действует на однократные шаги и на шаги без обязательного носителя; там решение остаётся за владельцем и записывается («шаг остаётся ручным, потому что …»), а не живёт молчаливым умолчанием.
>
> ## Случай
> MDMy: память проекта велась в приватном git-репозитории с первого коммита, но перенос в него был ручным и встал на `d85e2c84` от 19.06.2026 — за два месяца до того, как деструктивный тест 22.08.2026 стёр живую память. Замер по уцелевшему фрагменту указателя (180 имён, нижняя граница): 1 нашёлся в git, 11 — в живой памяти, 169 — нигде; из окна 19.06–22.08 не вернулось ничего. Репозиторий был; умер шаг. Решение исполнителя 24.08.2026: `infra/scripts/sync-memory.sh` (секреты → копирование → фиксация → push) + шлюз памяти в `deploy.sh` — выкат, единственный путь на прод, отказывает кодом 4, если файл живой памяти недостижим из удалённых веток.
>
> ## Связано
> - `enforced-rotation-for-self-stored-transient-data.md` — тот же принцип для растущих данных («ручная уборка = не считается»); тот стандарт — про данные и переполнение, этот — про шаги и потерю.
> - `git-dr-mirror-sync.md` — образец уже привязанного шага: push в зеркало «после **каждого** push», а не «по расписанию».
> - `scenarios/session-start.md` (гейт памяти) — отказ, а не напоминание, на старте сессии.

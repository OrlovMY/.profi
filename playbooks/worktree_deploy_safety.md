# Worktree Agent Deploy Safety — HARD RULES

**Создано после регрессии**: агент, работавший в git worktree, пересобрал и **сам задеплоил** web-bundle на прод-сервер, базируясь на устаревшей базе `master`. В git'е код был корректный, но бандл, который скачивал пользователь, — старый. Со стороны это выглядело как «всё сломано».

# Что НЕЛЬЗЯ делать в worktree-агенте

| Запрещено | Почему |
|---|---|
| `docker compose build` на прод-сервере | Build из stale worktree base → old bundle |
| `docker compose up -d --force-recreate` | Перетирает рабочий контейнер старым |
| `cp ...` в директорию статики / staging прода | Подкладывает stale артефакты в prod |
| `git push origin <branch>` | `master` не должен меняться агентом |
| Cherry-pick «для синхронизации» | Затягивает старые коммиты, перекрывая свежие |
| `git reset --hard` на `master` | Может удалить локальные правки |

# Что МОЖНО

| Разрешено | Условие |
|---|---|
| `git fetch "<абсолютный путь к главному рабочему каталогу>" master` + `git checkout -b <ветка> FETCH_HEAD` | **Обязательно** до начала работы. Не через ремоут — почему, см. «Mandatory pre-flight» |
| `git commit` в свою feature ветку | Только локально |
| Build / typecheck для проверки **синтаксиса** | Только в worktree, не на prod-сервере |
| SSH на прод для **read-only** диагностики (curl, logs, ls) | Без mutate |
| Применить миграцию при **explicit ask** в брифинге | Когда координатор явно написал «migration apply разрешена» |

# Страж изоляции может отвергнуть составную команду — дели на простые

В изолированной копии страж харнеса **может отвергнуть** составной вызов оболочки, где участвует git, — циклы, функции, heredoc с хвостовыми командами, длинные цепочки; какие именно, заранее не предсказать — признаком служит сам отказ «command is too complex to verify that it stays inside the worktree». Получив его — не повторяй ту же команду и не обходи стража: дели на простые одиночные вызовы; многострочную запись в файл — инструментом правки, не heredoc'ом с довеском. Это не отказ git и не запрет работы.

Случай: 24.08.2026, две независимые сессии (приёмка С7 и разбор PQ-01) — страж многократно отвергал составные вызовы; результат не пострадал, время терялось на повторные попытки. Граница: действует только в изолированной копии (`isolation:"worktree"`); вне её составные команды работают как обычно.

# Mandatory pre-flight для worktree-агента

В начале работы:
```bash
# 0. ГДЕ Я. Спрашиваем у git, а не у пути: в главном рабочем каталоге служебный
#    каталог и общий служебный каталог — одно и то же, в любой изолированной
#    копии они различаются.
test "$(git rev-parse --git-dir)" = "$(git rev-parse --git-common-dir)" \
  && echo "СТОП: это ГЛАВНЫЙ рабочий каталог, а не изолированная копия" \
  || echo "изолированная копия — можно работать"

# 1. Базу берём ИЗ ГЛАВНОГО РАБОЧЕГО КАТАЛОГА, по абсолютному пути, а не через ремоут
git fetch "<абсолютный путь к главному рабочему каталогу>" master
git checkout -b <ветка> FETCH_HEAD

# 2. Рабочее дерево чистое
git status

# 3. Базу подтверждаем ДВАЖДЫ — хешем и содержимым
git rev-parse --short HEAD          # сверить с хешем, названным в задании
ls <файл-маркер из задания>         # маркер обязан существовать
```

Хеш разошёлся или маркера нет — **СТОП**, сообщить координатору и не начинать работу.

**Шаг 0 совпал — тоже СТОП, и это более ранний отказ, чем все остальные.** Ты в главном рабочем каталоге, а не в копии: любая смена ветки здесь переключит её под всеми, кто работает параллельно, — чужие незакоммиченные правки окажутся на чужой ветке, а незавершённые слияния посреди дерева.

Проверка спрашивает **состояние, а не причину**: забыл ли координатор указать изоляцию, сорвалась ли она, запущен ли агент вручную — ответ один, и нужен именно он.

**Почему шаг 0 понадобился отдельно, хотя раздел заведён ровно против работы в главном каталоге.** Остальные шаги проверяют базу (чей код) и чистоту (не затру ли чужое), но не **принадлежность дерева**. Агент, выполнивший их целиком и добросовестно, по-прежнему не знает, где он. Случай 14.09.2026: агент документации был запущен без изоляции, правил файлы в главном каталоге и оставил главное дерево стоять на своей ветке при трёх работавших рядом кодовых агентах; исполнитель не мог этого заметить со своей стороны — признака не было. Последствий не случилось потому, что дерево оказалось чистым, а не потому, что что-то сработало.

**Почему именно равенство двух путей, а не путь и не вид `.git`.** Обе «наглядные» проверки неверны, и их не надо «упрощать» обратно:

* «не внутри ли я главного каталога» — **ложный СТОП**: копии агентов харнес кладёт ВНУТРЬ главного каталога (`<главный>/.claude/worktrees/<агент>`). 14.09.2026 такая проверка остановила бы три законно работавшие копии из трёх;
* `test -f .git` — **ложное разрешение**: при `git init --separate-git-dir` служебный каталог заменён файлом и в главном каталоге тоже;
* `git rev-parse --git-dir` сам по себе сравнивать не с чем: в главном каталоге он печатает относительное `.git`, и сравнение с абсолютным путём не совпадёт **никогда**, то есть проверка будет вечно-зелёной — ровно тот отказ, против которого пишется эта выноска.

Равенство `--git-dir` и `--git-common-dir` устойчиво к обоим случаям, потому что спрашивает у git, а не у файловой системы. Проверено 14.09.2026 на главном каталоге и трёх живых копиях, включая копию вне главного каталога и копию внутри него.

**Почему не через ремоут.** Имя ремоута — псевдоним: оно ничего не говорит о том, куда указывает и насколько отстало. Ремоутов у проекта обычно несколько (в проекте-источнике этого правила на 19.08.2026 их было четыре), их назначение менялось за одни сутки, а часть отставала на сотни коммитов. Настоящая основная ветка живёт в главном рабочем каталоге, и его путь однозначен.

Отставание любого ремоута измеряется одной строкой и **измеряется, а не предполагается**:

```bash
git fetch <ремоут> && git rev-list --count <ремоут>/master..master   # 0 = ремоут догнал НАС; иначе он отстал на столько коммитов
# ВНИМАНИЕ, это ДРУГОЙ вопрос, чем гейт перед ответвлением. Здесь спрашивают «догнало ли зеркало нас»,
# там — «не отстали ли МЫ»: git rev-list --count master..<ремоут>/master (scenarios/git-workflow.md, п.1).
# Направления противоположны, и перепутанное даёт ноль ровно в опасном состоянии.
```

**Считать после `fetch`.** Несвежим бывает и сам ремоут, и локальный ref, которым на него смотрят, — симптом одинаковый, неисправности разные, и без `fetch` их не различить. 19.08.2026 наблюдались обе разом: замороженное зеркало действительно отстало на полсотни коммитов, а `origin` за те же сутки сменил назначение, и ref обновился только после `fetch`.

**Величина живая: в тексте правила её не фиксируют, её получают командой.** Число, вписанное в правило, протухает быстрее правила и превращает верную мысль в неверный факт.

**Это не особенность изолированных рабочих копий.** Каталог `.git` у них общий с главным (`cat <рабочая копия>/.git` показывает `gitdir:` внутрь главного репозитория), и `origin/master` в них — тот же самый ref. Устаревает не ref копии, а сам ремоут.

**Проверка маркером не убирается** — она и должна ловить случаи, когда даже это не помогло.

**Обратная сторона, для координатора:** слияние тоже нельзя доверять ремоуту рабочей копии — готовую ветку забирать самому из главного каталога, у агента спрашивать только хеш финального коммита и имя ветки.

# Mandatory post-flight

Перед финальным отчётом:
```bash
# 1. Verify не сломал ничего на проде
ssh <prod-host> "curl -sk https://<app-host>/healthz"
ssh <prod-host> "docker exec <web-container> ls <static-dir>/assets | grep index-"
# Сравнить hash с тем, что был в начале (если это не deployment task)

# 2. Если bundle hash сменился без явного deploy в брифинге — REPORT regression
```

# В брифинге worktree-агенту ОБЯЗАТЕЛЬНО

```
### Permissions
- Bash/git/npm/go разрешены ВНУТРИ worktree.
- SSH на прод-сервер разрешён ТОЛЬКО для read-only diagnostics.
- ⛔ ЗАПРЕЩЕНО: `docker compose build/up`, `cp` в директорию статики/staging прода,
  `git push origin`, cherry-pick из других веток, `git reset --hard`.
- Deploy = координатор после merge ветки. Если не уверен → "ВОПРОС:" и стоп.
```

# Сигналы что агент нарушил правила

В его финальном отчёте:
- «Развёрнуто на проде»
- «web-контейнер пересобран и перезапущен»
- «Cherry-pick'нул `xxxxxxx` для синхронизации»
- «docker compose build clean → deployed»
- «Bundle обновлён в директории статики»

→ Это **red flag**. Немедленно re-build из текущего prod master ИЛИ rollback на предыдущий bundle.

```bash

# 2. Verify bundle hash сменился
ssh <prod-host> "docker exec <web-container> ls <static-dir>/assets | grep index-"

# 3. Force browser reload
# В Chrome: localStorage.clear() + hard reload
# Пользователю: «обнови страницу Ctrl+Shift+R»
```

# Сценарий: Git workflow

## Правило

Все новые фичи и фиксы разрабатываются в отдельных ветках. Слияние в `master` — только после завершения работы и успешного деплоя.

| Тип | Ветка | Источник |
|-----|-------|----------|
| Новая фича | `feat/<name>` | `master` |
| Фикс бага | `fix/<name>` | `master` |
| Hotfix (критично) | `hotfix/<name>` | `master` |
| Chore / infra | `chore/<name>` | `master` |

## Правила для агентов

1. **Ветка от master** — `git checkout master && git pull && git checkout -b feat/<name>` **перед** началом работы.
   **Гейт перед ответвлением:** `git fetch <ремоут>`, затем `git rev-list --count master..<ремоут>/master` обязан дать **0** — то есть в ремоуте нет ни одного коммита, которого нет у тебя.

   **Направление важно.** Обратный счёт (`<ремоут>/master..master`) измеряет, насколько ты **впереди**, и в состоянии «отстал» даёт ноль — пропуская ровно тот случай, ради которого гейт заведён. Проверено воссозданием условия отказа 19.08.2026, а не рассуждением: на искусственно отодвинутой базе (`master~N`) счёт в записанную сторону даёт **не ноль** — ловит, а в обратную — **ноль**, то есть пропускает. Конкретная величина здесь не приводится намеренно: она зависит от топологии мержей и у двух проверяющих вышла разной при одинаково верном выводе. Проверяется **признак «ноль / не ноль»**, а не число.

   **Почему гейт вообще нужен.** `git pull` тянет из ремоута, а имя ремоута — псевдоним: оно не говорит ни куда указывает, ни насколько свежо. Несвежими бывают оба конца, и оба случая наблюдались 19.08.2026 в проекте-источнике: замороженное зеркало отстало на полсотни коммитов (`fetch` его не двигал — запись туда была запрещена владельцем), а основной ремоут за те же сутки сменил назначение, и локальный ref, которым на него смотрели, обновился только после `fetch`. Поэтому **измеряют, а не помнят, и измеряют после `fetch`.** `<ремоут>` — тот, куда пишут сейчас; какой это ремоут — спрашивать не память, а `git remote -v` и запись в памяти проекта о действующем адресе записи.

   Число не 0 — дотянуть базу (`git pull <ремоут> master`) либо брать её из главного рабочего каталога (`playbooks/worktree_deploy_safety.md`), и только потом ответвляться.
2. **Коммиты только в свою ветку.** Прямая запись в `master` запрещена.
3. **Commit messages** — conventional commits:
   - `feat(scope): ...` — новая фича
   - `fix(scope): ...` — фикс
   - `chore(scope): ...` — служебное
   - `docs(scope): ...` — документация
   - `refactor(scope): ...` — рефакторинг без изменения поведения
4. **По завершении** — сообщить HR-D хэш коммита и готовность к merge (приёмка — по критериям `scenarios/task-template.md`, «Критерии приёмки»).
5. **Merge в master** — делает владелец интеграционного файла или DO-01 при деплое.

## Что запрещено без явного одобрения пользователя

- `git push --force` в master (или публичные ветки).
- `git reset --hard` на публичных ветках.
- `git rebase -i` интерактивный — не поддерживается в AI-workflow.
- `git commit --no-verify` — не пропускать hooks. Если hook падает — чинить причину, а не обходить.
- `git commit --amend` на опубликованных коммитах.
- Удаление веток, которые могут содержать непомёрдженную работу.

## Destructive Git Operations — всегда спрашивать

Перед выполнением:
- force push
- reset --hard
- branch -D (force delete)
- clean -fdx
- checkout -- / restore .

спросить пользователя явно и дождаться «да».

## Деплой через git bundle (стандарт)

Когда нет push-доступа к VPS, используется bundle-flow. **Критично:** на VPS перед `git fetch` в активную ветку обязательно отстёгивать HEAD: без этого git откажет — с сообщением, не молча, — а сборка всё равно запустится и соберёт старый код (подробно ниже, «Почему `--detach` обязателен»).

```bash
# Локально:
VPS_HEAD=$(ssh root@<remote_host> "cd <repo_path> && git rev-parse master")
git bundle create /tmp/<task>.bundle ${VPS_HEAD}..HEAD HEAD
scp /tmp/<task>.bundle root@<remote_host>:/tmp/

# На VPS — ВСЕГДА detach перед fetch в master:
ssh root@<remote_host> "cd <repo_path> && \
  git checkout --detach && \
  git fetch /tmp/<task>.bundle HEAD:master && \
  git checkout master && \
  git log --oneline -3"
```

**Почему `--detach` обязателен:** git отказывает `fatal: refusing to fetch into branch 'refs/heads/master' checked out at '<path>'`. Без detach git **отказывает и говорит об этом** — команда не молчит. Молчит следующий шаг: сборка запускается независимо от исхода получения кода, `git reset --hard master` указывает на старый ref, артефакты пересобираются со старого, и пользователь видит регресс. **Опасна не тишина команды, а отсутствие шлюза между получением кода и сборкой** — поэтому проверка ниже обязательна, а не желательна.

**Всегда** проверять `git log --oneline -3` после fetch — не доверять «fetch finished without errors».

## Деплой через push (если есть post-receive hook)

```bash
git push vps master    # автоматический deploy
```

В этом случае merge в master = деплой. Политика веток становится критичной — никто не пушит в master то, что не готово к продакшну.

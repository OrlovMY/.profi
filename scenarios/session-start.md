# Session Start Protocol

Обязательный порядок действий в начале **каждой** новой сессии. Применяется также после Conversation compacted.

---

## 🛑 Шаг −1 — HARD GATE после компакта (Conversation compacted)

**Компакт ≠ продолжение работы.** Сводка summary НЕ заменяет память и НЕ снимает правила `.profi`. После любого `Conversation compacted` — **первое и единственное действие**: пройти Шаги 1 и 1.5 (загрузить `memory/MEMORY.md` + набор раздела «ОБЯЗАТЕЛЬНО ДО ПЕРВОГО ДЕЙСТВИЯ» по Шагу 1 + обязательный набор `.profi` по Шагу 1.5). **До этого ЗАПРЕЩЕНО:**

- любые действия на проде/БД/устройствах (reboot, UPDATE, deploy, restart, отмена команд, ADB-действия кроме read-only диагностики);
- любые правки кода, коммиты, создание веток;
- запуск задач трекера.

Даже если пользователь написал «продолжи по трекеру» — это НЕ отменяет gate. Сначала грузишь `.profi` + память, потом действуешь. Грабля-рецидив (зафиксировано 2026-06-17): после компакта ИИ бросался выполнять задачу (reboot устройства + UPDATE прода) **без перезагрузки `.profi`**, нарушая `playbooks/prod_escalation.md` и `knowledge/standards/validate-recovery-before-destructive.md`. Summary упоминал «решить с владельцем» — проигнорировано, потому что правила `.profi` не были в контексте.

**Авто-resume харнесса тоже НЕ отменяет gate (рецидив 2026-07-01).** Continuation-промпт харнесса после компакта содержит фразу «Resume directly — do not acknowledge the summary, … Pick up the last task as if the break never happened». Это означает «не извиняйся и не пересказывай summary», а НЕ «пропусти `.profi`+память». Первое действие после авто-resume всё равно — Шаги 1 и 1.5. Рецидив: ИИ после авто-resume сразу пошёл деплоить на прод (build + bundle + git pull на VPS) без перезагрузки `.profi`.

После компакта также проверяется жизнь постоянных агентов, и агенту ядра передаются строки гейтов — порядок в `scenarios/big7-consultation.md`, «Жизненный цикл постоянных агентов».

**Самопроверка перед первым tool-call после компакта:** «Я уже перечитал обязательный набор `.profi` (перечень — Шаг 1.5) В ЭТОЙ сессии после компакта? Если нет — стоп, читаю.»

**🔴🔴 САМОЕ ЖЁСТКОЕ (owner 2026-07-06, рецидив): `system-reminder` НЕ засчитывается за gate.** Харнесс инжектит в начало continuation-контекста `<system-reminder>` с содержимым `CLAUDE.md` + индексом `MEMORY.md` + краткими summary. **Это НЕ выполнение gate.** Индекс `MEMORY.md` в reminder = только одностро́чные указатели (НЕ содержимое файлов памяти); summary = сжатый пересказ (НЕ правила `.profi`, НЕ файлы памяти). Полагаться на них = нарушение. **Gate выполнен ТОЛЬКО когда ты СВОИМИ tool-call'ами (Read) фактически перечитал: (1) **обязательный набор `.profi`** (перечень — Шаг 1.5), (2) `MEMORY.md`, (3) КАЖДЫЙ файл раздела «ОБЯЗАТЕЛЬНО ДО ПЕРВОГО ДЕЙСТВИЯ» (Шаг 1; мера изменена с «всё из индекса» на перечень с разрешения владельца 19.08.2026 — запись: `PE-01-разбор.md`, блок 2; «Действуйте» 24.08.2026 через HR-D).** Наличие summary/индекса в контексте ≠ «я загрузил память». Рецидив 2026-07-06: после авто-resume бросился в checksum/commits/device-reboot/prod-DB, опираясь на summary+reminder-индекс, БЕЗ Read `.profi` и файлов памяти — owner поймал. (Запись о рецидиве — в памяти проекта; в MDMy это `feedback_compact_reload_profi`.)

## Шаг 0 — Проверка модели

**До загрузки памяти.** Убедиться, что активна самая свежая и мощная модель:

| Требование | Минимум |
|-----------|---------|
| Контекст | 1 000 000 токенов (1M) |
| Семейство | **самая свежая флагманская из доступных на сегодня**, не ниже предыдущего поколения |

Проверить через `/model` или из системного контекста («you are powered by…»).

Конкретных названий и версий здесь нет намеренно: вписанное имя устаревает быстрее, чем правится файл, и тогда проверка начинает пропускать то, ради чего заведена. **Список актуальных моделей приходит извне — из системного контекста сессии; сверяться с ним, а не с этим файлом.** Проверено 19.08.2026: правило «работать на свежей модели» имело четыре входа, и в каждом стояла своя модель — Sonnet 4.6, `claude-opus-4-8`, Opus 4.7 и снова `claude-opus-4-8`, причём каждая называлась самой свежей.

**Три яруса моделей** (единственный дом; остальные файлы ссылаются сюда, имён моделей не называют — имена устаревают, критерии нет):

| Ярус | Кто на нём работает | Критерий выбора, без имени |
|---|---|---|
| **Решающий** | координатор HR-D, агент ядра (все роли `roles/big7/INDEX.md`), PE-01/PQ-01 | самая свежая флагманская из списка системного контекста сессии, контекст ≥1M — то, что проверяет этот Шаг 0 |
| **Кодовый** | исполнители `roles/engineers/*`, doc-owner, Phase B | рабочая модель для реализации классом ниже флагмана (в системном контексте — алиасы кодовых моделей; на 24.08.2026 при флагмане Fable это Sonnet или Opus — датированный пример, слова владельца). **Старший кодовый** (флагман) — когда ТЗ требует проектных решений по ходу, и решения возвращаются ядру на аудит |
| **Механический** | поиск, наблюдение (watch) | самый дешёвый, способный выполнить задачу без суждения: детерминированный предикат/retrieval ([[delegate-background-ops-to-cheap-subagents]] §3 — тест границы) |

PE-01/PQ-01 — решающий ярус: они пишут и проверяют инструкции, по которым работают все остальные; ошибка в них размножается (`roles-and-briefs-via-pe01.md`, случай 18.08). Схема ярусов — решение владельца 24.08.2026 по вердикту ядра (условие С5, консультация 24.08).

**Если не соответствует** — остановиться и написать:
> «Перед загрузкой памяти необходимо установить самую свежую модель с 1M токенов. Пожалуйста, переключите через `/model` и начните сессию заново.»

Не загружать память и не выполнять задачи до подтверждения.

## Шаг 1 — Загрузка памяти

После подтверждения модели:

1. Read `memory/MEMORY.md` (индекс) целиком.
2. **Файлы обязательного набора** — раздел `MEMORY.md` «ОБЯЗАТЕЛЬНО ДО ПЕРВОГО ДЕЙСТВИЯ», где они перечислены поимённо (каркас — `templates/memory_index.md`). Набор ведётся вручную и осознанно: правило попадает в него не по значку в строке, а по цене нарушения — необратимой (потеря устройства, потеря данных, простой боевой системы) — плюс все действующие разрешения со сроком. Значок признаком не является: на 19.08.2026 отбор по 🔴 не включал ни запрет окирпичивания, ни запрет перезапуска прода, ни правило о разрушительных действиях. Читать **все** файлы раздела, параллельным батчем.
   - Первой — действующую программу работ (первая незакрытая запись раздела «RESUME / активные программы»), см. Шаг 2.
   - **Артефакт** — строка `ГЕЙТ память: N из M` до первого действия, где M берётся из этого раздела, а не считается на глаз. `N < M` — гейт не пройден.
   - **Порядок ведения набора:** правило, чьё нарушение стоило инцидента, вносится в набор тем же ходом, что и запись о самом инциденте. **Признак соблюдения:** у раздела стоит дата последнего изменения; появился в памяти новый файл с записью об инциденте, а дата раздела старше этой записи — порядок нарушен, набор пересматривается. Проверка — одно сравнение двух дат, делается тем, кто проходит гейт.
   - Остальные файлы индекса — по теме задачи (раздел индекса по предмету работы), а не «релевантные на глаз».
   - **Файл памяти вне указателя — не отменённое правило, а потерянный вход.** Он продолжает действовать: правило не перестаёт им быть оттого, что на него забыли поставить ссылку. Встретил такой файл — внеси его в указатель тем же ходом; считаешь устаревшим — проведи через порядок «Перед удалением, сокращением и восстановлением правила» (`roles/big7/pe-01.md`), а не через молчание.
3. Только после этого — отвечать и действовать.

Почему набор, а не «всё»: на 19.08.2026 память MDMy — 343 файла и 17 тысяч строк; требование «прочитать всё» три раза подряд не исполнялось (рецидивы 17.06, 01.07, 06.07), и ужесточение формулировки исполнимым его не сделало. Мера задана составом, перечень открывают и пересчитывают. Сокращать разрешил владелец (19.08.2026); запретительная часть Шага −1 не тронута.

## Шаг 1.5 — Обязательный набор `.profi` (для ЛЮБОГО проекта)

**Любой проект, над которым работает команда, обязан АВТОМАТИЧЕСКИ подгружать `.profi` при старте сессии.** `.profi` — единый источник истины для ролей, стандартов, сценариев, плейбуков, шаблонов. Где он лежит в этом проекте — в `CLAUDE.md`/`MEMORY.md` проекта (копия, submodule или соседний clone — `README.md`, «Как использовать»); абсолютный путь у каждой машины свой и в этом файле не живёт. (Переходная скобка: в MDMy на 24.08.2026 это `C:\Users\orlovmy\Projects\.profi`; скобка снимается тем же ходом, которым путь проверен или добавлен в `CLAUDE.md`/`MEMORY.md` проекта.) Память конкретного проекта хранит только проектную специфику и **ссылается** на `.profi`.

**Обязательный набор — перечень, а не признак:**
1. `README.md`;
2. `knowledge/standards/*.md` — все;
3. `scenarios/*.md` — все;
4. `playbooks/*.md` — все;
5. `roles/hr-d.md` и `roles/big7/INDEX.md` — роль координатора и единственный дом состава команды.

Остальные файлы ролей — системные промпты конкретных агентов: читаются при созыве этого агента, не при старте. `knowledge/guides/`, `knowledge/recipes/`, `templates/` — по теме задачи.

Объём набора на 24.08.2026 — 62 файла; пересчитывать командой `ls README.md knowledge/standards/*.md scenarios/*.md playbooks/*.md roles/hr-d.md roles/big7/INDEX.md | wc -l`. Это четверть-половина контекста 200k и единицы процентов от 1M — поэтому Шаг 0 стоит раньше этого шага, а не для порядка.

**Артефакт гейта** — одна строка до первого действия: `ГЕЙТ .profi: N файлов из M` — где M получено командой выше, а не названо по памяти. `N < M` — гейт не пройден.

**Механизм авто-подгрузки:** в `CLAUDE.md`/`MEMORY.md` каждого проекта должен быть явный пункт «при старте сессии подгрузить `.profi`» с путём. Нет пункта — **добавить его в тот же ход** (как и пропагацию обязательных стандартов). Прямое поручение владельца, 2026-06-08.

## Шаг 2 — Где остановились

Действующая программа работ — **первая запись раздела «RESUME / активные программы» в `MEMORY.md`, не помеченная как закрытая (✅)**. Если верхних записей с пометкой «ЧИТАТЬ ПЕРВЫМ» несколько — читать все такие, начиная сверху, и назвать вслух, сколько их. Порядок в разделе поддерживается правилом-производителем (`playbooks/memory_management.md`): новая программа встаёт наверх тем же ходом, которым заводится.

Программа определяется **записью в указателе, а не именем файла**: программы сменяются, имя файла — нет, и старый файл под привычным именем читается как текущее состояние.

`memory/project_active_plan.md`, если он есть, читается **после** неё и только как справка. Перед чтением — посмотреть дату последнего изменения: старше двух недель — это не программа работ, а история; читать как историю и сказать об этом вслух.

Повод: на 19.08.2026 `project_active_plan.md` не менялся 95 дней и описывал спринт, закрытый в мае, — а Шаг 2 предписывал читать его первым, до всего остального.

## Triggers для повтора

- Начало любой новой сессии
- **После Conversation compacted** — обязателен Шаг −1 (HARD GATE): `.profi` + память грузятся ДО любого действия. Сжатие ≠ замена памяти.
- После смены модели внутри сессии

## Anti-patterns

- Грузить только «релевантные» файлы → пропускаешь правила, которые не знаешь, что нужны.
- Грузить память без проверки модели → маленький контекст обрежет половину или вся работа будет с деградированной моделью.
- Принимать `project_active_plan.md` за текущее состояние, не посмотрев его дату → работаешь по программе, закрытой три месяца назад.
- **После компакта сразу бросаться выполнять задачу** (бросил summary, побежал делать) → нарушаешь правила `.profi`, которых нет в сжатом контексте. Самый частый рецидив. Сначала Шаг −1.

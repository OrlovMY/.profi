# No Regression — изменения только улучшают

**Строгое правило.** Любое изменение роли, стандарта, правила работы, плейбука или сценария должно только улучшать результат. Ухудшение недопустимо.

---

## Что это означает на практике

Перед внесением любого изменения в `.profi` или память проекта — ответить на три вопроса:

1. **Что конкретно улучшится?** (скорость, качество, безопасность, предсказуемость)
2. **Что может ухудшиться?** Если есть хоть один регресс — изменение не принимается в текущем виде.
3. **Есть ли способ получить улучшение без ухудшений?** Если да — только этот способ.

---

## Применяется к

- Ролям агентов (`roles/`)
- Сценариям и плейбукам (`scenarios/`, `playbooks/`)
- Стандартам качества (`knowledge/standards/`)
- Правилам работы команды
- Feedback-правилам в памяти проекта
- Шаблонам (`templates/`)

## Как проверить перед изменением

```
До изменения:  [описать текущее поведение / результат]
После:         [описать новое поведение / результат]
Регрессы:      [перечислить всё что может стать хуже]
Вывод:         УЛУЧШЕНИЕ / РЕГРЕСС (не принять) / НЕЙТРАЛЬНО (не нужно)
```

Если вывод — **РЕГРЕСС**, изменение останавливается. HR-D эскалирует в Большую команду с описанием trade-off.

**Где форма записывается.** В теле самого изменения, а не в переписке. Для `.profi`: если правка прошла разбор PE-01/PQ-01 — записью этого разбора (поля «Было / Стало / Почему / Проверено существованием» у PE-01 и вердикт PQ-01 — это и есть заполненная форма, **при условии, что в записи разбора по этой правке есть строка «Регрессы: …» — что может стать хуже, — либо у PE-01, либо в вердикте PQ-01; нет строки — форма не заполнена**), а в правленом файле и в сообщении коммита — одна строка-адрес: `История правок: <файл разбора>, пункт <N>, <дата>`. Если правка меняет смысл, а разбора PE-01/PQ-01 не было (указание владельца, правка после инцидента) — форма абзацем «История правок» в правленом файле, как прежде. Если правка смысла не меняет (`roles/big7/pq-01.md`, «Когда ты подключаешься») — форма не требуется. Для памяти проекта — абзацем в правленом файле под заголовком «История правок». Для кода — в описании коммита. **Незаписанная форма считается незаполненной**: 19.08.2026 форма была введена и в тот же день не заполнена ни в одном из изменённых тем же коммитом файлов — потому что запись требовалась в файле, а работа велась в разборе.

**Когда обязательна:** удаление правила, изменение его смысла, изменение роли, изменение порядка эскалации, любые требования безопасности.
**Когда не требуется:** опечатки, разметка, битые ссылки, даты — то есть правки, не меняющие объёма действия. Решение о разряде перепроверяет тот, кто принимает правку, — **самому себе разряд не назначают**.

Повод: на 19.08.2026 в своде и памяти **ноль** заполненных экземпляров этой формы при обязательном требовании — единственное вхождение строки «Регрессы:» во всём своде — сам шаблон выше. Требование без места записи не выполняется и обесценивает соседние.

## Частые ловушки

- **Упрощение ради краткости** — сокращение правила может убрать важный edge case.
- **«Это редко нужно»** — редкий случай, не покрытый правилом, становится инцидентом.
- **Переписывание вместо дополнения** — новый опыт должен дополнять старое правило, не заменять его без явного обоснования что старое было неверным.
- **Восстановление не по оригиналу** — текст правила, собранный по ссылкам и пересказам, объявляет это в первой строке и в `description`; порядок — `roles/big7/pe-01.md`, «Перед удалением и восстановлением правила».
- **Ускорение за счёт пропуска шагов** — убрать шаг верификации «чтобы быстрее» = регресс качества.

## Продвижение улучшений в стандарт

Если изменение прошло проверку (нет регрессов) и команда согласована — оно **немедленно становится стандартом**:

1. Обновить соответствующий файл в `.profi` (роль / сценарий / плейбук / стандарт)
2. Если изменение выявлено в ходе работы над проектом — зафиксировать в памяти проекта (`feedback_*.md`) со ссылкой на `.profi`
3. Сообщить HR-D — он обновляет `MEMORY.md` и при необходимости бриефинги агентов

**Триггеры для фиксации** — см. `scenarios/post-incident-memory-update.md`. Ключевые: пользователь подтвердил улучшение, Большая команда проголосовала, инцидент показал пробел в правиле.

**Правило:** улучшение, не зафиксированное в `.profi`, не является стандартом — оно существует только в голове одной сессии и будет потеряно.

## Исключения

Допускается изменение, которое ухудшает один параметр, если:
- Большая команда явно проголосовала за trade-off
- Пользователь дал явное одобрение с пониманием последствий
- Ухудшение задокументировано и принято осознанно (записать в изменяемый файл комментарием)

История правок: `PE-01-разбор-2026-08-24.md`, раздел «Совместная редакция и применение», П12; вердикты — `PQ-01-разбор-2026-08-24.md`; 2026-08-24.

История правок: `ревизия-свода-2026-08-24.md`, раздел 12 (Д1-ход: канон «Большая команда», решение владельца 25.08.2026); вердикты — `PQ-01-ревизия-2026-08-24.md`, дополнение по разделу 12; 2026-08-25.

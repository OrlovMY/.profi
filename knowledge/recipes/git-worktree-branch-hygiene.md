# Recipe: уборка git worktrees + старых веток (после серий worktree-агентов)

## Условия применения
Проект, где coding-агенты работают в изолированных git worktree (`isolation: "worktree"`). Со временем `.claude/worktrees/agent-*` + одноимённые ветки накапливаются, если не чистить после merge. Симптом: сотни локальных веток, десятки/сотни зарегистрированных worktree, locked-worktree пинят даже смерженные ветки.

## 🔴 Прежняя редакция этого рецепта ДВАЖДЫ разрушила среду разработки

Здесь до 23.09.2026 стояла команда, которую надо знать в лицо, потому что её
уже скопировали и выполнили:

```bash
# ❌ НИКОГДА. Эта строка стояла в своде и дважды опустошила node_modules.
… | grep '/.claude/worktrees/agent-' | while read -r wt; do
    git worktree unlock "$wt" 2>/dev/null
    git worktree remove --force "$wt" 2>/dev/null
  done
```

`--force`, в цикле, по всем сразу, без единой проверки на связи наружу.
Исполненная дословно, она прошла сквозь соединение каталогов (junction) и
**вычистила настоящие `node_modules` основного чекаута**:

  (`memory/feedback_worktree_junction_empties_the_original`). В тот же вечер,
  **уже зная про ловушку**, тот же человек разрушил каталог ВТОРОЙ раз: он
  проверил на связи **пять копий из двадцати пяти**, а связь была в одной из
  непроверенных;

🔴 **Главное, ради чего этот абзац стоит в самом рецепте: свод велел делать то,

веток и locked-worktree») — свалку разбирают уже второй раз.

**У `git worktree remove` НЕТ холостого прогона.** Замер 23.09.2026:
`git worktree remove -h` → `usage: git worktree remove [-f] <worktree>`,
единственный флаг `-f`. Значит предохранителем служит **предполётная проверка,
а не флаг**, и снять её нечем.

## Суть (по убыванию безопасности)

1. **Worktrees — безопасно ТОЛЬКО с предполётной проверкой.** Удаляется
   рабочая папка, НЕ ветка; коммиты остаются в refs — **но только у копии, у
   которой ветка есть.** У отсоединённых обещание не действует: см. врезку в
   конце шага 1.1.

   **Шаг 1.1. Собрать полный перечень — шире, чем `agent-`.** Замер
   23.09.2026: связанных копий 118 (строк в `git worktree list` — 119,
   первая из них сам основной чекаут; счёт ведут ПОСЛЕ `tail -n +2`), фильтр
   прежней редакции
   (`grep '/.claude/worktrees/agent-'`) покрывал **97**, а 21 связанную копию
   не видел вовсе — 19 заведённых руками `…/MDMy-wt-*`, одна в `%TEMP%`
   (`wt-memguard`) и одна с другим префиксом (`.claude/worktrees/wf_…`).
   **Исполненный дословно, рецепт оставил бы пятую часть свалки молча.**

   🔴 **Перечень собирается ПАРАМИ «путь + ветка», а не одними путями.** Три
   строки предполётной проверки (1.3) требуют имя ветки, а откуда взять его
   для конкретного пути, прежняя редакция не говорила нигде: на 118 копиях
   исполнитель либо изобретёт свой способ, либо откроет каждую руками. Одним
   проходом:

   ```bash
   git worktree list --porcelain | awk '
     /^worktree /{p=substr($0,10)}
     /^branch /{print p"\t"substr($0,8)}
     /^detached/{print p"\tDETACHED"}' | tail -n +2 > /tmp/копии.txt
   wc -l < /tmp/копии.txt            # 118 на 23.09.2026
   grep -c DETACHED /tmp/копии.txt   # 3 на 23.09.2026 — в обычную уборку НЕ идут
   ```
   Путь и ветка разделены табуляцией. Ветка приходит полным именем
   (`refs/heads/fix/…`) — в `git branch -d` и `git rev-list` подставляют её
   как есть либо срезают `refs/heads/`, но **одинаково во всех трёх строках**
   проверки, иначе сравнение имён разойдётся молча.

   🔴 **`tail -n +2` обязателен: первой записью `git worktree list` идёт САМ
   основной чекаут.** Расширив фильтр и забыв про это, вы наведёте уборку на
   главное дерево. (`git worktree remove` откажется его удалять, но полагаться
   на это не надо: отказ — не замысел, а частность реализации.) Перечень
   дальше просматривают глазами и вычёркивают всё, что не подлежит уборке.

   🔴 **КОПИЯ БЕЗ ВЕТКИ (`DETACHED`) РАЗБИРАЕТСЯ ОТДЕЛЬНО, И ОБЕЩАНИЕ
   «коммиты остаются в refs» НА НЕЁ НЕ РАСПРОСТРАНЯЕТСЯ.** Замер 23.09.2026:
   из 119 записей 116 со строкой `branch` и **3 со строкой `detached`**, то
   есть 115 копий с веткой и 3 в отсоединённом HEAD. У таких копий ветки нет
   вовсе: в строки 1–2 предполётной проверки подставить нечего, а после
   `worktree remove` + `prune` их коммиты становятся недостижимыми и уходят
   при сборке мусора. Пункт 3 рецепта бережёт ветки и на отсоединённые копии
   не распространяется ни словом — поэтому порядок задаётся здесь:

   ```bash
   git -C '<копия>' log --oneline -5          # посмотреть, что там вообще есть
   git rev-list --count <main>..HEAD          # выполнять В КОПИИ (git -C)
   ```
   - **неслитых ноль** — удалять как обычную копию, по общему порядку;
   - **не ноль** — **сперва завести ветку**, и только потом удалять:
     ```bash
     git -C '<копия>' branch save/<осмысленное имя>
     ```
     Имя осмысленное, а не порядковый номер: ветку `save/17` через месяц не
     откроет никто, и она превратится в такую же свалку.

   **Вслепую отсоединённую копию не удалять никогда.** Разница с обычной в
   том, что там ошибка стоит рабочей папки, а здесь — коммитов, которых больше
   нигде нет.

   **Шаг 1.2. Снять связи наружу — ДО удаления копии, по одной.**
   🔴 **Это ЕДИНСТВЕННАЯ защита от разрушения чужого каталога** — не первая и
   не главная из нескольких: единственная. Ни отсутствие `--force`, ни
   **четыре первые** строки предполётной проверки от связи не спасают
   (доказательство — таблица замера в шаге 1.4); спасает **пятая**, и она
   отсылает сюда же. Строки 1–4 берегут РАБОТУ (слитость, неслитые коммиты,
   незакоммиченное, блокировка); от чужого каталога бережёт только пятая.

   **Почему тут пересчитаны строки, а не сказано «пять».** В первой правке по
   К1 здесь стояло «ни пять строк предполётной проверки от связи не спасают» —
   а пятая строка той таблицы и есть этот самый шаг 1.2. Читающий буквально
   получал основание считать таблицу не относящейся к связям и **пропустить
   самую дорогую её строку** — рекурсивную проверку каждой из 118 копий.
   Прежний ложный признак говорил «без флага не страшно», этот говорил бы
   «таблица не про связи»; оба ведут в одно место — к пропуску поиска связей.

   Связь делает «содержимым» копии чужой каталог, и сила `--force` относится
   не к тому, о чём думаешь, когда её пишешь.

   ```powershell
   # Найти точки повторного разбора (junction/symlink) и НАЗВАТЬ ИХ ЦЕЛЬ.
   # 🔴 Контроль вырождения ПЕРЕД поиском: пустой вывод при нуле просмотренных
   # узлов означает «не проверяли», а не «связей нет».
   $копия = '<копия>'
   if (-not (Test-Path -LiteralPath $копия)) { throw "путь не разобран: $копия" }
   $узлы = Get-ChildItem -LiteralPath $копия -Recurse -Force -ErrorAction SilentlyContinue
   "просмотрено узлов: $($узлы.Count)"      # ноль при существующем пути = признак ослеп
   $узлы | Where-Object { $_.Attributes -band [IO.FileAttributes]::ReparsePoint } |
     ForEach-Object { $_.FullName + '  ->  ' + $_.Target }
   ```
   🔴 **Вывод этого блока НЕ пропускать через конвейер.** `throw` даёт код
   возврата 1, но конвейер подменяет его кодом последней команды — проверено
   23.09.2026: тот же вызов через `| head` вернул **0**, то есть отказ
   превратился в успех. В проекте это записанный класс
   (`memory/feedback_never_pipe_deploy_output`), и здесь он стоит ровно там,
   где цена — чужой каталог.

   **Снятие ограничения глубины проверку НЕ утяжеляет — это замерено, а не
   предположено.** Опасение понятное: раз рекурсия без предела, не пойдёт ли
   она внутрь связи и не встанет ли на 118 копиях. Замер 23.09.2026:
   `Get-ChildItem -Recurse -Force` по копии со связью на каталог из 26 узлов
   вернул **1 узел** — саму связь, внутрь не пошёл; `find` без `-maxdepth` дал
   2 строки. Признаки остаются быстрыми, зацикливания нет.

   Цель важна не меньше самой связи: удалять нельзя, пока не знаешь, **что
   именно** будет уничтожено. Проверено подсадкой 23.09.2026 — на заведённой
   нарочно связи признак назвал и путь, и цель; на копии без связей молчит.

   🔴 **Ограничения глубины здесь НЕТ, и это не небрежность.** В первой
   переписке стояло `-Depth 3` (и `-maxdepth 3` у второго признака). Замер
   23.09.2026: связь на глубине 5 — **оба признака молчат**, `find` без
   ограничения её находит. Вместе с абзацем про `--force` в шаге 1.4 это был
   полный путь к третьему разрушению **без единого отступления от текста
   рецепта**: junction в `apps/web/node_modules` (глубина ≥ 4) → признаки
   молчат → пять строк проверки сходятся → удаление без `-f` идёт сквозь связь
   → чужой каталог пуст, код возврата `0`, рецепт выполнен дословно.
   Понадобится ограничить глубину ради скорости — **напишите вслух, до какого
   уровня смотрели**, и считайте молчание признака за пределами этого уровня
   неизвестностью, а не отсутствием связи.

   🔴 **Контроль вырождения обязателен, потому что молчание признака читается
   как разрешение.** `-ErrorAction SilentlyContinue` на несуществующем пути
   даёт пустой вывод **без ошибки** (проверено), и «пусто» неотличимо от
   «связей нет». У второго признака краснота при неверном пути есть (`find`
   возвращает 1), но её убирает типовое `2>/dev/null`, которое дописывают
   против шума `Permission denied` — **поэтому его здесь и не дописывают**.
   Число просмотренных узлов печатается всегда: ноль при существующем пути
   означает, что признак ослеп.

   Нашлась связь — **сперва снять её, и только `cmd rmdir` по самой связи**:
   ```bash
   cmd //c rmdir "<путь до связи>"
   ```
   🔴 **`rmdir` из Git Bash здесь НЕ РАБОТАЕТ** — замер 23.09.2026: отвечает
   `Not a directory`, потому что видит соединение как ссылку, а не каталог.
   Проверено обоими способами на нарочно заведённой связи: `cmd //c rmdir`
   снял связь, в цели остался файл, как и был. **Ни `rm -rf`, ни `--force`** —
   оба идут по содержимому, то есть в чужой каталог.

   Второй признак, на случай если первый ослепнет: `find '<копия>' -type l`
   — **без `-maxdepth` и без `2>/dev/null`** (см. два красных абзаца выше).
   В моём замере 23.09.2026 он соединение **увидел**, но память
   проекта записывает случай, когда проверка из Git Bash соединения не видела
   вовсе. Поэтому признака два, и **срабатывание ЛЮБОГО запрещает удаление**,
   а молчание обоих — разрешает.

   **Шаг 1.3. Предполётная проверка КАЖДОЙ копии, а не выборки.** Именно
   выборка (5 из 25) привела ко второму разрушению. Перед удалением по каждой
   копии обязаны сойтись пять ответов. **Строки 1–2 требуют имя ветки — берут
   его из пары в `/tmp/копии.txt` (шаг 1.1); у копии с пометкой `DETACHED`
   подставлять нечего, и она идёт не сюда, а во врезку про отсоединённые.**

   | Что | Чем меряется | Что обязано быть |
   |---|---|---|
   | ветка слита | `git branch --merged <main> \| sed 's/^[*+] *//; s/^ *//'` содержит ветку копии — **`+` срезается обязательно**: занятую копией ветку git печатает именно с ним, и проверка на голое имя даёт ноль на всех копиях | да |
   | неслитых коммитов ноль | `git rev-list --count <main>..<ветка>` | `0` |
   | незакоммиченного ноль | `git -C '<копия>' status --porcelain` | пусто |
   | копия не заблокирована | `git worktree list --porcelain` — нет `locked` | нет |
   | точек повторного разбора внутри ноль | шаг 1.2, оба признака | пусто |

   Хоть один ответ не такой — **копия не удаляется**, а разбирается отдельно.
   **Строки 1–4 берегут РАБОТУ, строка 5 — чужой каталог.** Это разные виды
   ущерба, и пропуск пятой стоит дороже: незакоммиченное лежит в копии,
   которую видно, а опустошённый каталог обнаруживается через сутки и не там.

   🔴 **Признак «живые процессы внутри копии» в порядок НЕ входит, и это
   решение, а не пропуск.** Проверяющий ловит сам себя: поиск имени копии в
   командных строках находит собственные измерительные команды, то есть
   признак даёт красное и зелёное вне связи с предметом. Его работу закрывают
   строки про незакоммиченное и блокировку: занятая копия почти всегда грязная
   либо заблокирована, а если нет — удалять её безопасно.

   **Шаг 1.4. Удалять по одной, БЕЗ `--force`.**
   ```bash
   git worktree unlock '<копия>' 2>/dev/null   # только если блокировка разобрана
   git worktree remove '<копия>'               # без -f
   ```
   🔴 **СНЯТИЕ `--force` НЕ ЗАЩИЩАЕТ ОТ СВЯЗИ. Единственная защита — шаг 1.2.**
   Здесь в первой переписке 23.09.2026 стояло «отсутствие `--force` и есть
   страховка». **Это неверно, и неверно опасно:** прочитав такое, исполнитель
   ослабит предполётную проверку — а она после этого и остаётся единственным,
   что стоит между ним и чужим каталогом.

   Замер, воспроизведённый дважды (PQ-01 и мной, отдельный стенд-репозиторий,
   23.09.2026):

   | шаг | значение |
   |---|---|
   | копия чистая | `git -C <копия> status --porcelain` → пусто |
   | копия не заблокирована | `locked` в `git worktree list --porcelain` нет |
   | внутри junction `node_modules` → каталог с 4 файлами | `node_modules/` в `.gitignore` |
   | `git worktree remove <копия>` **без флага** | **код возврата `0`** |
   | файлов в цели ДО / ПОСЛЕ | **4 / 0** |

   Почему так: без флага команда отказывается только на **грязной** и на
   **заблокированной** копии. Копия со связью не является ни той, ни другой —
   `node_modules` игнорируется, значит копия чиста, удаление идёт штатно,
   сквозь связь, без единого предупреждения и с успешным кодом возврата.

   **Тогда зачем `--force` всё равно убран.** Он снимает отказ на грязной и
   заблокированной копии, то есть уносит незакоммиченную работу, — это
   отдельная и реальная цена. Но **причиной обоих опустошений `node_modules`
   был не флаг, а связь**, и лечится она только шагом 1.2. Отказ без флага
   по-прежнему сообщение («предполётная проверка что-то упустила»), его
   разбирают, а не давят флагом; но молчание этой команды **не доказывает
   ничего** о связях.

   **Шаг 1.5. После каждой десятки — сверять, что общий каталог цел.**
   ```bash
   ls '<АБСОЛЮТНЫЙ путь основного чекаута>/console/node_modules' | wc -l   # 413 на 23.09.2026
   ```
   🔴 **Путь только абсолютный.** Здесь стоял относительный
   `console/node_modules`: запущенный из копии, он померил бы каталог САМОЙ
   КОПИИ и показал здоровье не того места — то есть сторож здоровья сам стал
   бы слепым ровно там, где нужен.
   Число берут ДО начала уборки и сверяют по ходу. Десятка, а не конец
   прогона: в обоих случаях разрушение обнаружилось «не сразу и не там», и чем
   позже оно найдено, тем дороже разбор.

   **Шаг 1.6. В конце — `git worktree prune`.** Он не снимет те копии, чья
   папка ещё на диске, поэтому идёт последним, а не первым.

   🔴 **Граница проверенного — назовём её, чтобы её не приняли за общее
   правило.** Все замеры выше (23.09.2026, PQ-01 и PE-01) сделаны на **одной
   версии git** и **одной форме связи — соединении каталогов (junction,
   `mklink /J`)**. Символьные ссылки на каталоги (`mklink /D`) и поведение при
   включённом `core.symlinks` **не проверялись**, и там всё может быть иначе —
   в обе стороны. Встретив такую связь, действуйте по тому же порядку
   (обнаружить → снять → только потом удалять), но **не ссылайтесь на замеры
   выше как на доказательство**: их предмет другой.
2. **Merged-ветки — безопасно, но ПО ОДНОЙ.**
   ```bash
   git branch --merged <main> | grep -vE '^\* |^\+ *<main>$|^ *<main>$' \
     | sed 's/^[*+] *//; s/^ *//' \
     | while read -r б; do
         git branch -d "$б" || echo "ОТКАЗ по ветке: $б"
       done
   ```
   🔴 **`xargs` заменён циклом:** залп там, где рецепт сам требует «по одной».
   При отказе на одной ветке `xargs` не останавливается и перечень сделанного
   не восстанавливается — а именно перечень и нужен, когда разбираешь отказ.
   Цикл называет отказавшую ветку поимённо.
   🔴 **Срезается и `+`, а не только `*`.** Ветку, занятую рабочей копией, git
   печатает с префиксом `+`. Замер 23.09.2026: из веток, слитых в `master`,
   **114 идут с `+`** — то есть проверка на голое имя не сработала бы ни на
   одной из 118 копий. `-d`, не `-D` — откажется на несмерженном. Подставить имя основной ветки (`main`/`master`). Фильтр заякорен: неякорный `<main>` выбрасывал любую ветку с подстрокой main/master в имени (`maintenance-fix`, `domain-cleanup`) — тихо и без ошибки. Выполнять стоя на `<main>` (или предварить `git checkout <main>`): фильтр `--merged` сверяет с `<main>`, а `git branch -d` следом — с ТЕКУЩИМ HEAD; с другой ветки влитые получают ложное «not fully merged», толкающее к `-D` (случай — `git-branch-discipline.md`, выноска при аудите, 25.08.2026).
3. **Unmerged-ветки — ОСТОРОЖНО:** по каждой `git log --oneline <main>..<branch>` → решить superseded vs уникальное. Superseded (фича реализована иначе/в проде, эксперимент) → `git branch -D`. Уникальное → оставить + сообщить владельцу. **Не удалять вслепую.**

## Антипаттерны
- ❌ **`git worktree remove --force`** — снимает отказ на грязной и
  заблокированной копии, то есть уносит незакоммиченную работу.
- ❌ **Считать, что БЕЗ `--force` удаление безопасно.** Замер 23.09.2026:
  чистая незаблокированная копия со связью внутри, `git worktree remove` без
  флага → код возврата `0`, в цели было 4 файла, стало 0. От связи защищает
  только шаг 1.2.
- ❌ **Искать связи с ограничением глубины** (`-Depth 3`, `-maxdepth 3`) и
  читать молчание как «связей нет»: связь на глубине 5 обоими признаками не
  видна.
- ❌ **Глушить краснуху признака** (`-ErrorAction SilentlyContinue` без
  проверки пути, `find … 2>/dev/null`): пустой вывод неотличим от «не
  проверяли» и читается как разрешение удалять.
- ❌ **Проверять на связи ВЫБОРКУ копий.** Пять из двадцати пяти — и связь
  оказалась в одной из непроверенных. Обход дешёвый, копий десятки, одной
  непроверенной достаточно.
- ❌ **Снимать связь через `rm -rf` или удалять копию, не сняв связь.**
  Удаление идёт по содержимому, а связь делает «содержимым» чужой каталог.
- ❌ **Заводить связь на общий `node_modules` в копию, которую потом удалят.**
  Не создавать причину дешевле любой защиты при уборке — см. строку в шаблоне
  задания (`scenarios/task-template.md`).
- ❌ Не чистить worktree после merge → накопление (реальный кейс: сотни веток и worktree).
- ❌ `git branch -D` по `--no-merged` массово без проверки `<main>..branch` → потеря работы.
- ❌ Делать уборку «на лету» без плана/трекера/документации и без явного «да» владельца — деструктив требует одобрения, а сам факт уборки фиксируется как задача (даже housekeeping ведётся по стандарту проекта).
- ❌ Трогать основную ветку, деплой-ref, текущую ветку.

## Лучшая практика

**Убирать копию при ПРИЁМКЕ работы, а не пакетом раз в месяц.** Это не
пожелание об опрятности, а единственный способ не попасть в ту ситуацию, где
случились оба разрушения: **пакетная уборка и есть тот случай, где проверяют
выборку.** Одну копию при приёмке проверяют целиком, потому что она одна;
двадцать пять — проверяют пять, потому что двадцать пять долго. Так и вышло
05.09.

🔴 **Корень, который рецептом не чинится, и это надо знать заранее:
заведение копий АВТОМАТИЧЕСКОЕ (`isolation: "worktree"`), а уборка РУЧНАЯ.**
Замер 23.09.2026: ни один хук и ни одна настройка в `.claude/` слова
`worktree` не упоминают вовсе. Правило проекта: шаг, который надо ВСПОМНИТЬ,
рано или поздно забывают — и забывают тем вернее, чем больше работы. 118
копий накопились именно так, по одной, и каждая по отдельности была незаметна.
**Пока уборка не привязана к действию, которое и так совершается (приёмка
ветки, слияние), рецепт остаётся лечением, а не профилактикой.** Заведение
такой привязки — решение владельца проекта, а не правка этого рецепта.

Периодический прогон шагов 1–2 — как поддерживающая работа; шаг 3 — ревью.

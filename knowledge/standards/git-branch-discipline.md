## Политика веток
1. **Разработка ВСЕГДА на отдельной ветке** (`feat/<name>` или `fix/<name>` от свежего master). Прямые коммиты в master запрещены — **без исключений, включая документацию**. Оговорка «кроме тривиальных доков» снята 19.08.2026 вместе с таким же исключением в §Правила-1: два исключения в одном файле, оба неизвестного происхождения, при запрете, за которым стоит записанный инцидент.
2. **Держать ≤1–2 активных dev-веток.** Не плодить. Если срочно потребовался фикс в другом месте — допустимо завести 2-ю ветку, НО обязательно ВЕРНУТЬСЯ и доделать первую.
3. **Готовое решение = merge в master** (`--no-ff`). Только после завершения+верификации (+деплоя для прод-фич). **Сразу после мержа ветка УДАЛЯЕТСЯ — локально И на ВСЕХ remote (адрес записи + зеркала).** Это часть ритуала мержа, не «потом» (см. §0 ниже).
4. **master всегда актуален** — отражает прод. **ИНВАРИАНТ: на любом remote и локально НЕ должно быть ни одной ветки, уже влитой в master.** Существуют только: `master`, deploy-ref (напр. `vps-master`), и ≤1–2 активных НЕвлитых dev-веток. Влитая ветка, оставшаяся жить = нарушение, чистится немедленно.
5. **Перед стартом новой ветки** — закрыть/смержить текущую (или явно зафиксировать почему держим параллельно — срочность).
6. **Долгоживущую ветку** регулярно подтягивать к master (`git merge master`), иначе дрейф → деплой откатит чужое (см. инцидент ниже).

**Обоснование:** дивергентные осиротевшие ветки = источник «фикс есть в репо, но не в проде» (фикс ушёл на одну ветку, деплой потерял роут другой фичи). Единая линия master = единый источник истины, нет потери выкаченных фич.

## Проблема, которую предотвращаем
Фикс был закоммичен на feature-ветку, которая ответвилась от СТАРОГО master (до того как на master приехала другая фича — новый эндпоинт). Деплой этой ветки собрал бинарь, в котором **прод-фича отсутствовала** (роут пропал) → ошибка авторизации в проде. Симптом коварен: и фикс, и фича по отдельности «есть в репо», но НЕ в одном коммите.

## §0. Ритуал мержа = merge + delete (НЕРАЗДЕЛИМО)

«Слил в master → ветка перестала существовать». Мерж НЕ считается завершённым, пока ветка не удалена везде. Канонический ритуал (после завершения+верификации+деплоя):

```bash
git checkout master && git merge --no-ff feat/<name> -m "merge: ..."
git push <адрес-записи> master   # какой ремоут — git remote -v + память проекта, не это правило
# push в зеркало — по git-dr-mirror-sync.md; действующие приостановки/прекращения — в памяти проекта
# ↓ СРАЗУ, тем же заходом — удалить ветку отовсюду:
git branch -d feat/<name>                            # локально (-d сам откажет если не влита)
git push <адрес-записи> --delete feat/<name>
# то же для зеркала, если оно пишущее — см. git-dr-mirror-sync.md
git remote prune <адрес-записи>
```

(Переходно: в MDMy на 24.08.2026 адрес записи — GitHub; GitLab — только чтение/архив, решение владельца 18.08 + 24.08. Скобка снимается ходом, которым запись подтверждена в памяти проекта.)

Исключение (ветку НЕ мержим и НЕ удаляем) — только если она **намеренно НЕ влита** и ждёт внешнего гейта (напр. on-device smoke перед merge). Такие держим, но их должно быть ≤1–2 и каждая с записанной причиной «почему ещё не влита».

### Периодический аудит инварианта (≥0 влитых веток)
Раз в сессию/после серии мержей — проверить, что влитых веток не осталось ни локально, ни на remote:
```bash
# локальные влитые (кроме master/deploy-ref):
git for-each-ref --format='%(refname:short)' refs/heads/ \
 | grep -vE '^(master|vps-master)$' \
 | while read b; do git merge-base --is-ancestor "$b" master 2>/dev/null && echo "MERGED(local): $b"; done
# remote влитые (по каждому remote):
git fetch --all -p -q
for r in origin <mirror>; do for b in $(git for-each-ref --format='%(refname:short)' refs/remotes/$r/ | grep -vE "/(HEAD|master)$"); do
  git merge-base --is-ancestor "$b" master 2>/dev/null && echo "MERGED($r): ${b#$r/}"; done; done
```
Любая строка `MERGED(...)` → удалить эту ветку (см. ритуал). Должно быть пусто.

> **Пустой вывод сам по себе ничего не доказывает.** До 19.08.2026 скрипт печатал пусто **потому, что не работал**: он сверялся с именем ветки, которого в проекте нет. Прежде чем принять пустой вывод за «нарушений нет», убедиться, что имя ветки в скрипте — настоящее (`git rev-parse --abbrev-ref HEAD`).
>
> **Непустой вывод — это либо нарушение, которое чистят немедленно, либо записанный в памяти проекта долг уборки.** Долг обязан иметь запись с датой снятия: оговорка «пока не убрано — непустой вывод ожидаем» без даты превращается в постоянную и через квартал объясняет любому, почему двести строк можно не читать. Пример по этому классу: в проекте-источнике 19.08.2026 сразу после починки имени ветки скрипт дал **226 строк `MERGED(local)` при 239 локальных ветках** — долг записан со сроком до первой ревизии свода (26.08.2026); текущее состояние долга — в памяти того проекта, не здесь. (Переходно: до подтверждённой записи долга в памяти MDMy этот пример — единственная его запись; скобка снимается ходом, которым запись подтверждена.)

## Правила (выполнять ВСЕГДА)

### 1. Перед любым коммитом — проверь активную ветку
`git branch --show-current` (или `git status` сверху). Коммить ровно туда, куда задумано:
- мелкий фикс/серверное изменение → на `fix/<name>` от свежей основной ветки. **Прямая запись в основную ветку запрещена без исключений, включая документацию.** Исключение «мелкий фикс → сразу в основную» снято 19.08.2026: происхождение строки не найдено, случаев при ней не записано, а за запретом стоит записанный инцидент (шапка файла). Обнаружившийся случай, для которого ветка действительно избыточна, заводится заново **через владельца**, а не восстановлением строки: запрет, за которым стоит инцидент, исключениями молча обрастать не должен;
- изменение в составе незавершённой фичи → на её feature-ветку.
Не коммить «куда оказался переключён» после возни с ветками/stash.

### 2. Feature-ветку ответвляй от СВЕЖЕГО master
`git checkout master && git pull && git checkout -b fix/<name>`. **Гейт перед ответвлением:** `git fetch <ремоут>`, затем `git rev-list --count master..<ремоут>/master` обязан дать **0** — в ремоуте нет ни одного коммита, которого нет у тебя. **Направление важно:** обратный счёт (`<ремоут>/master..master`) измеряет, насколько ты впереди, и в состоянии «отстал» даёт ноль, пропуская тот самый случай, ради которого гейт заведён (см. `scenarios/git-workflow.md`, п.1). Если ветка живёт долго, пока master ушёл вперёд — **смержи master в неё перед деплоем** (`git merge master`), иначе деплой ветки откатит чужие прод-фичи.

### 3. Перед деплоем — убедись, что коммит содержит ВСЁ ожидаемое
Деплоить из единой линии (`master`), не из ad-hoc ветки. Проверка-чеклист перед сборкой:
- `git branch --show-current` = ожидаемая ветка;
- `git merge-base --is-ancestor <последний-задеплоенный-коммит> HEAD` → деплоим потомка, не дивергента (не теряем уже выкаченное);
- grep ключевых строк прод-фич в рабочем дереве (напр. роут/хэндлер), которые ДОЛЖНЫ быть.

### 4. Чистый деплой на сервер (не «грязный pull»)
`git pull <bundle> HEAD` при расхождении **отказывает с сообщением**. Молча собирается СТАРЫЙ working-tree — потому что сборку никто не связал с исходом получения кода. Правильно:
```
git fetch <bundle> HEAD
git checkout --detach FETCH_HEAD
git branch -f master FETCH_HEAD && git checkout master
git reset --hard FETCH_HEAD   # убрать грязный working-tree
grep -c '<ключевая строка фичи>' <файл>   # верификация ПЕРЕД build
```

### 5. После деплоя — верифицировать что задеплоено то самое
curl/grep на проде: фича отвечает, ключевой код присутствует в развёрнутых исходниках. «git push OK» ≠ «в проде нужный бинарь».

### 6. Сведение веток
Если фикс уехал не туда — не передеплоивать обрывок: **смержить расходящиеся ветки в одну линию** (`git checkout master && git merge --no-ff <ветка>`), убедиться что объединённый коммит содержит всё, и деплоить его.

## Быстрый предполётный чеклист (перед commit→deploy)
1. `git branch --show-current` — та ветка?
2. содержит ли HEAD последний прод-коммит? (`merge-base --is-ancestor`)
3. grep ключевых строк всех ожидаемых фич в рабочем дереве;
4. деплой: fetch + detach + reset --hard + grep-верификация ПЕРЕД build;
5. после: curl/grep на проде.

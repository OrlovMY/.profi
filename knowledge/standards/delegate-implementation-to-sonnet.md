# Standard: реализацию — агентам кодового яруса, решающий только аудитирует

> Имя файла — исторический след (модель на дату заведения); действующий ярус — `scenarios/session-start.md`, Шаг 0.

**Статус:** обязательный · **Применимость:** ВСЕ проекты, все роли (особенно координатор — решающий ярус)

## Правило

Подготовленную и **полностью понятую** задачу (есть чёткий промпт/ТЗ: что делать, какие файлы, ограничения, критерии приёмки, как верифицировать) — **передавать на реализацию агенту кодового яруса (`scenarios/session-start.md`, Шаг 0)**, а не писать код самой.

**Высокоуровневая модель (решающий ярус / координатор) код НЕ пишет.** Её работа:
1. **Понять и подготовить** — исследование, декомпозиция, проектирование, написание точного промпта/ТЗ для агента.
2. **Делегировать** — `Agent(subagent_type, model: <кодовый ярус>, prompt: <полное ТЗ>)` (или Workflow с моделью кодового яруса на стадиях реализации).
3. **Аудитировать** код агента — корректность, безопасность, регрессии, соответствие стандартам/паспортам, naming-contract, edge-cases. Возврат на доработку через того же/нового кодового агента.

За высокоуровневой моделью остаётся: исследование, проектирование, написание промптов, **аудит/ревью**, координация, принятие решений, прод-операции под approval. **Написание прикладного кода — нет.**

## Когда применять

- Задача **понятна и подготовлена** → сразу делегировать кодовому + аудит. Не садиться писать самому.
- Задача **ещё не понята** → сначала высокоуровневая модель исследует/проектирует (это её работа), доводит до однозначного промпта → потом делегирует кодовому.
- **Старший кодовый (флагман)** — когда ТЗ требует проектных решений по ходу; такие решения возвращаются ядру на аудит (`scenarios/session-start.md`, Шаг 0, таблица ярусов).

## Почему

- Дорогой контекст/токены высокой модели тратятся на то, что кодовый ярус делает хорошо и дешевле. Высокая модель максимально ценна в декомпозиции, ловле граблей и **независимом ревью**.
- Разделение «исполнитель ≠ аудитор» повышает качество: аудит чужого кода строже, чем самопроверка только что написанного.
- Масштабируется: один координатор готовит и проверяет работу нескольких кодовых исполнителей параллельно.

## Как применять (чек-лист)

1. Довести задачу до однозначного промпта (файлы/пакеты, что нельзя трогать, контракт имён, критерии приёмки, команды верификации, ветка).
2. `Agent`/`Workflow` с моделью кодового яруса (+ нужный `subagent_type`/`isolation:'worktree'` для параллельных правок).
3. Получить diff/отчёт → **аудит**: собирается ли, нет ли регрессий, безопасность, стандарты, паспорт обновлён.
4. Не прошло — вернуть кодовому агенту с замечаниями. Прошло — принять, закоммитить/задеплоить (ops/approval — за координатором).

## Переиспользование агента (не плодить свежих)

Для **последовательной/связанной** работы и **итераций после ревью** — продолжать через `SendMessage(to: '<agentId>')` тому же агенту: он уже в контексте кода/находок, не платит повторный рамп-ап. Сохранять agentId спавненных агентов. Правки после аудита diff'а возвращать ТОМУ ЖЕ агенту (см. `agent-review-loop-before-finish`).

**Новый агент оправдан только когда:** нужна реальная параллельность (N агентов разом на file-disjoint задачах — один не делает параллельно); read-only Plan-агент не может править (нужен отдельный editing-агент); принципиально несвязанная область, где старый контекст бесполезен.

## Антипаттерны

- Высокая модель «быстренько сама поправит пару строк» вместо делегирования — нарушение (кроме разве что правки самого промпта/ТЗ/доков/памяти).
- Делегировать **непонятую** задачу — сначала исследование/проектирование, иначе кодовый исполнитель получит мусорное ТЗ.
- Принять код агента без аудита.
- **Плодить свежих агентов под каждый под-шаг** вместо `SendMessage` существующему in-context агенту (теряешь контекст, платишь повторный рамп). Новый — только по условиям выше.

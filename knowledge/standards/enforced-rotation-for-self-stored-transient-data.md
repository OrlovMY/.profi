# Standard: строгая ротация/retention для ВСЕХ само-сохраняемых транзитных данных (HARD)

**Статус:** обязательный · **Применимость:** все проекты; любой компонент (сервер, устройство/агент, VPS, БД), который САМ пишет растущие во времени данные.
**Происхождение:** директива владельца 2026-07-08 (MDMy/CPE): «все временные данные, такие как логи, которые мы сами сохраняем, должны строго ротироваться, чтобы избежать переполнения; срок хранения в каждом случае индивидуально».

## Правило
**Любой само-генерируемый растущий во времени артефакт ОБЯЗАН иметь заложенную (enforced) ротацию/retention с самого момента введения — иначе он рано или поздно переполнит хранилище.** «Строго» = ограничение реально применяется кодом/крон/движком (не «договорённость почистить потом»). Retention (срок/размер) выбирается **индивидуально** под каждый артефакт, но НУЛЕВОЙ/безлимитной ротации быть не должно.

Покрывает (не только «логи»): app/service-логи, watchdog/decision-логи, диагностические дампы (pre-reboot снимки), буферы/спулы (pending-очереди, недоставленные батчи), кэши, upload-таблицы (device_logs и т.п.), time-series телеметрия, аудит-таблицы, temp-файлы, которые пишутся периодически.

## Обязательные требования (design-time gate)
1. **Bound задаётся ДО ввода артефакта** (в паспорте/ТЗ фичи, рядом с наименованием артефакта): по **размеру** (макс. байт/строк) И/ИЛИ по **возрасту** (макс. дни), в зависимости от природы. Часто — оба (что раньше сработает).
2. **Enforcement автоматический:** ротация/усечение/удаление выполняется самим кодом (ring-buffer, truncate-on-size, `DELETE ... WHERE ts < now()-interval`, logrotate-аналог, cap N последних), а НЕ ручной уборкой. Ручная уборка = не считается.
3. **Учитывать УЗКОЕ хранилище, а не только «диск большой».** На стеснённых носителях (embedded/IoT `/data` на несколько ГБ, eMMC) bound жёстче и обязателен; переполнение там = кирпич/сбой, не просто «место кончилось». (Ср. `resource_tracking` — Retention policies; `transient-artifacts-cleanup` — не копить транзит.)
4. **Оба конца пайплайна:** если данные текут device→сервер (или agent→backend), ротация нужна И на источнике (файл на устройстве), И в приёмнике (таблица/хранилище). Усечение при передаче (48КБ хвост) НЕ заменяет ротацию исходного файла на устройстве.
5. **Wear-aware на flash:** на eMMC/SD минимизировать частоту перезаписи (писать при изменении, не каждый тик) — bound не должен провоцировать постоянный churn.
6. **Документировать bound** в паспорте артефакта (что за данные, где хранятся, лимит размера/возраста, механизм enforcement) — по нему можно проверить, что переполнение невозможно (documentation-first).

## Как применять (чек-лист при добавлении любого растущего артефакта)
- [ ] Назвал артефакт и место хранения (файл/таблица/путь).
- [ ] Задал лимит: размер и/или возраст (индивидуально).
- [ ] Enforcement в коде/крон/движке (не «потом руками»).
- [ ] Проверил УЗКОЕ хранилище (device /data, eMMC) — bound достаточно жёсткий.
- [ ] Оба конца (источник + приёмник) ограничены.
- [ ] Записал bound в паспорт.

## Антипаттерны
- ❌ Пишем лог/дамп/буфер «пока хватает места», ротацию «добавим позже» → позже = инцидент переполнения.
- ❌ Ротация только в приёмнике (БД capped), а файл-источник на устройстве растёт безлимитно.
- ❌ «Диск большой, переполнение маловероятно» на стеснённом носителе.
- ❌ Ротация есть, но выполняется ручной уборкой/скриптом ad-hoc (не enforced).

## Связано
- `transient-artifacts-cleanup` (не копить deploy-бандлы/build-выхлоп/кэши — тот же принцип для транзита на VPS).
- `resource_tracking` (playbook) — Retention policies для растущих таблиц; триггеры «логи без ротации → диск».
- `documentation-first-golden-rule` / `doc-completeness-fix-on-miss` — bound в паспорте.

## Источник
Владелец 2026-07-08 (MDMy/CPE), при разборе device-side логов CPE (риск переполнения `/data` ~2.5ГБ логами api.log/CONN_WATCHDOG_LOG/prereboot): «само-сохраняемые временные данные должны строго ротироваться, срок хранения индивидуально; зафиксировать правилом в .profi».

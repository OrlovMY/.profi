# Standard: делегировать background-операции (polling / monitoring / wait-for-condition) дешёвым персистентным субагентам

**Статус:** обязательный · **Применимость:** все проекты, любой момент, когда нужен фоновый цикл наблюдения/поллинга/ожидания условия.
**Происхождение:** директива владельца 2026-07-08 → вердикт Большой 7 (APPROVE). Сестринский паттерн к [[delegate-search-to-persistent-haiku]] (тот же механический ярус, персистентно; retrieval = найти факт, background-ops = ждать условие).

## Rationale
Каждый тик `Bash run_in_background` + чтение результата расходует контекст/токены координатора (решающий ярус). Background-bash к тому же самозавершается — длинные наблюдения требуют перезапуска. Вынос цикла в персистентного дешёвого субагента переносит итерации в ЕГО контекст; координатор получает только **дистиллят** (итог/значимое событие), не сырые тики.

## §1. Что делегировать (scope)
- Поллинг-до-условия (build_number ≥ N на устройстве, checkin-статус, файл/процесс появился, миграция применилась).
- Deploy/apply-мониторы, soak-watch, ожидание сходимости внешнего процесса.
- Любой цикл «крутить и ждать наступления условия».

## §2. Что НЕ делегировать (остаётся у координатора)
- **Решение-по-результату** (деплой / откат / эскалация) = суждение → решающий ярус (координатор/ядро).
- **Разрушающие / прод-мутирующие действия** (reboot / deploy / UPDATE / ADB-non-read-only). Watch-агент **READ-ONLY**: детектирует условие и возвращает; действие принимает координатор через нормальные prod-гейты (`prod_escalation` / `validate-recovery-before-destructive` не обходить).
- Интерпретация неоднозначного результата.

**🔴 Исключение — owner-авторизованный ПОВТОРЯЮЩИЙСЯ retry-dispatch (owner 2026-07-12, дважды).** Когда owner прямо санкционировал повторяющуюся ОГРАНИЧЕННУЮ идемпотентную операцию (напр. «гоняй retry OTA-раскатки на устройство X пока не встанет»), ВЕСЬ цикл — включая re-dispatch (прод-write) — живёт в дешёвом агенте механического яруса, НЕ в координаторском фоновом bash. Это перекрывает буквальное «прод-мутирующее→координатор» выше для узкого класса: (а) owner явно авторизовал конкретную операцию, (б) ограниченная (один device / фикс-артефакт), (в) идемпотентная (тот же cpe_ota, health-gate+rollback защищают), (г) координатор всё равно судит ИТОГ (verify-гейт) и НЕОБРАТИМЫЕ развилки (reboot→owner). Рационал owner: не жечь токены/контекст координатора на поллинг-с-редким-действием. Общее «прод-write→координатор» держится для НЕ-санкционированных/незапланированных/масштабных мутаций. Credential-hygiene: дешёвый агент НЕ пишет секрет в отдельный .sh/tmp-файл (inline в команде; классификатор флагнул persistent cred-файл).

## §3. Выбор модели (граница простое ↔ суждение)
- **Механический (по умолчанию)** — условие остановки записывается как ДЕТЕРМИНИРОВАННЫЙ предикат: сравнение чисел (`build ≥ 110`), grep-совпадение (лог содержит строку), булев (HTTP 200 / файл есть / процесс жив).
- **Кодовый** — цикл требует суждения на каждом тике (многофакторное «здоров ли деплой», неоднозначные логи, решение продолжать/прервать по качественному признаку).
- **Тест границы:** «можешь записать условие остановки как детерминированный предикат?» да → механический, нет → кодовый.
- Действие по итогу — **ВСЕГДА координатор** (решающий ярус; спорное — ядро), не watch-агент любой модели.

## §4. Механика
- Запуск `Agent run_in_background`, **персистентный** (переиспользуется через SendMessage для следующих наблюдений; «персистентный» = reuse, не «никогда не возвращается» — агент возвращает дистиллят текущего наблюдения и ждёт след. задачи через SendMessage, как агент ядра / поисковый).
- 🔴 **Watch ЖИВЁТ В ПЕРСИСТЕНТНОМ СУБАГЕНТЕ, НЕ в main-треде (owner 2026-07-08, усилено).** Прогонять `Monitor`/поллинг из координатора = тратить контекст координатора на тики — запрещено. Координатор ТОЛЬКО спавнит/реюзит watch-агента и получает дистиллят. (Ранее был обратный workaround «Monitor из main, т.к. дешёвая модель не крутит цикл» — ОТМЕНЁН owner'ом: не тащить watch в main, а научить агента блокироваться правильно.)
- 🔴 **Механизм ожидания внутри watch-агента = инструмент `Monitor` (until-loop), НЕ самонарративный «цикл» в промпте.** Дешёвая модель НЕ умеет «сама крутить цикл с паузой» по текстовой инструкции — делает одну проверку и возвращается. Брифинг watch-агента ОБЯЗАН явно: «используй инструмент **Monitor** с until-условием X и таймаутом T (ОДИН вызов), эмить только на смену состояния/terminal, по завершении верни дистиллят». Foreground `sleep` заблокирован — Monitor штатный механизм блокирующего ожидания. Если watch-агент всё равно возвращается рано, не получив условия — переспавнить/дослать ему через SendMessage «продолжай Monitor до X», НЕ забирать watch в main.
- Явное условие остановки (детерминированный предикат) + **TIMEOUT** (не бесконечно).
- Возвращает ТОЛЬКО итог при достижении условия ИЛИ значимое событие/аномалию — **НЕ сырые тики**.
- **Реюз через SendMessage** для следующих наблюдений (как агент ядра / поисковый); связанная работа → тот же agentId (копит familiarity, не платит рамп-ап).
- Токен-экономика: тики живут в контексте субагента, координатор получает дистиллят.

## §5. Границы / анти-паттерны
- Прямой `Bash run_in_background` остаётся ОК **только для одноразовой быстрой команды без цикла** (сборка, разовый запрос, единичный scp). Есть цикл / ожидание-условия → watch-агент.
- **Cap:** не плодить вечные watch-агенты (ср. [[agent-question-rendezvous]] §2) — реюзить существующий через SendMessage, закрывать по завершении программы наблюдения.
- Watch-агент не действует на проде/устройстве — только наблюдает.
- Секреты в возвращаемом итоге — как `file:line`, НЕ значения (наследуется от search-стандарта / SEC-02).

## §6. Связь / иерархия делегирования
Сестринский паттерн к [[delegate-search-to-persistent-haiku]] (тот же механический ярус, персистентно; retrieval = найти факт, background-ops = ждать условие).
Иерархия: **механический (retrieval | watch) → кодовый (impl | judgment-loop) → решающий (coord / action-decision; ядро — audit)**. Дешёвые ДЕЛАЮТ механическое (найти/ждать); решающий ярус СУДИТ и ДЕЙСТВУЕТ.

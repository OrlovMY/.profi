# Standard: документацию вести отдельному ПОСТОЯННОМУ Sonnet-агенту

**Статус:** обязательный · **Применимость:** все проекты, любая работа с проектной документацией (паспорта функций/механизмов, контракт-доки, README модулей, OpenAPI, doc-home таксономия).
**Происхождение:** директива владельца 2026-07-08 (проект MDMy/CPE). Сестринский паттерн к [[delegate-implementation-to-sonnet]] (код) и [[delegate-search-to-persistent-haiku]] (поиск).

## Правило (load-bearing принцип)
**Написание и поддержка документации — отдельная делегируемая роль, закреплённая за ОДНИМ персистентным Sonnet-агентом («doc-owner»), а не за координатором и не за случайными агентами.** Координатор (Opus) СУДИТ (что должно быть задокументировано, полнота, приоритет, аудит doc↔код), но САМ доки не пишет — формулирует ТЗ и отдаёт doc-owner-агенту; тот пишет/правит/консолидирует, коммитит и пушит.

Разделяющая линия консистентна с иерархией делегирования:
**Haiku = retrieval → Sonnet(impl) = код → Sonnet(doc-owner) = документация → Opus = координация/суждение/аудит → Big-7 = решение.**
Дешёвые/специализированные ДЕЛАЮТ (найти/кодить/писать доки), Opus/Big-7 СУДЯТ и решают.

## 1. Что делегировать doc-owner-агенту ✅
- Написание/обновление паспортов (`docs/passports/**`), контракт-доков, README модулей, OpenAPI-описаний.
- Консолидация размазанной документации в единый источник (doc-home таксономия), перенастройка ссылок, устранение дублей-источников-истины.
- Синхронизация doc↔код при изменении контракта (в том же PR — правило [[documentation-first-golden-rule]] / doc-completeness-fix-on-miss).
- Фиксация найденных фактов в правильный doc-дом (по ТЗ координатора: «вот факты X с file:line — оформи паспорт»).

## 2. Что остаётся у координатора (Opus) ⛔
- **Суждение**: что должно быть задокументировано, достаточна ли полнота (критерий: по доке localize проблему БЕЗ чтения исходников), приоритет.
- **Аудит** написанного doc-owner-агентом (соответствие фактам/коду, нет регресса, doc-home верный).
- Сбор фактов для доки — это retrieval → [[delegate-search-to-persistent-haiku]] (Haiku находит file:line+цитаты → координатор формирует ТЗ doc-owner-агенту). Координатор НЕ грепает сам, НЕ пишет доку сам.

## 2.5. 🔴 Стартовый брифинг doc-owner (ОБЯЗАТЕЛЬНО, owner 2026-07-08)
**При первом спавне doc-owner в сессии координатор ОБЯЗАН передать ему ВЕСЬ свод правил ведения документации — до первой doc-задачи**, чтобы агент оформлял всё по стандарту с первого раза (а не переучивался правками). Без брифинга агент не знает doc-home таксономию, конвенции паспортов и HARD-правила проекта → оформит криво.

**Bundle брифинга (передать/указать прочитать):**
1. **Универсальные doc-стандарты `.profi`:** [[documentation-first-golden-rule]] (паспорт до кода, критерий «localize без чтения исходников»), [[doc-completeness-fix-on-miss]] (doc-home таксономия — где что живёт/куда дописывать), формат паспорта (п. 2 ниже), [[data-pipeline-naming-contract]] (единое имя по слоям), [[agent-review-loop-before-finish]] (возврат на аудит, не самозавершение), [[git-dr-mirror-sync]] (пуш во все зеркала), [[capture-findings-immediately]], [[safe-wording-avoid-false-block]] (нейтральные формулировки тем железа/прошивок).
2. **Проектные конвенции доков:** структура `docs/passports/**` (области/подпапки), формат паспорта (что делает / триггер / вход-выход / контракт / диагностика по слоям), главный контракт-док проекта (пример из MDMy: `agent-admin-server-contract.md`), единые источники истины (какие паспорта — канон), UI-каталог паспортов если есть, git-политика доков (ветка/прямо в master, коммит-конвенция, зеркала).
3. **Проектные HARD-правила, влияющие на формулировки доков** (напр. CPE: red-zone идентификаторов, no-pipe/LF-only при примерах команд).

Брифинг даётся ОДИН раз на сессию (агент персистентный, помнит). При реюзе в той же сессии — только конкретное ТЗ. **Чек координатора перед первой doc-задачей:** «передал ли я doc-owner полный свод правил?» Нет → сначала брифинг.

## 3. Механика
- **Один персистентный Sonnet-агент** на проект («doc-owner»), реюз через SendMessage (копит знание структуры доков проекта). Не плодить свежих под каждую правку.
- **Первый вызов в сессии = брифинг (§2.5) + первая задача.** Последующие — только ТЗ.
- Модель = sonnet. Tools: Read/Edit/Write/Grep/Glob/Bash (для git-коммита+пуша доков, включая зеркала — [[git-dr-mirror-sync]]).
- Doc-owner **завершает doc-задачу полностью**: пишет → self-verify (рендер/ссылки/нет битых якорей) → коммит в ветку/доки-политику проекта → пуш во все remote → возвращает координатору хэш+summary на аудит ([[agent-review-loop-before-finish]]).
- Аудит координатора обязателен перед «готово» (doc-owner исполняет, Opus судит).

## 4. Границы / анти-паттерны
- ❌ Координатор «быстренько сам поправит паспорт» — нарушение (кроме правки памяти проекта/`.profi` и коротких ТЗ; сами проектные доки — doc-owner).
- ❌ Писать доку в worktree-агенте, который параллельно меняет код той же области без владельца-интеграции (file-ownership) — доки-файлы тоже имеют владельца (doc-owner).
- ❌ Плодить разные источники истины (два паспорта про одно) — doc-owner консолидирует в один + ссылки.
- ✅ Мелкая строка в памяти/`.profi`/трекере — координатор сам (это не проектная документация в смысле паспортов).

## 5. Пропагация
Универсальный стандарт, источник истины здесь (`.profi`). **В памяти каждого проекта — строка-указатель** в `MEMORY.md` с `[[...]]` (как для delegate-implementation-to-sonnet / delegate-search-to-persistent-haiku). При старте в новом проекте: нет записи → добавить в тот же ход.
